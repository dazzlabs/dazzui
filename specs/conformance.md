# Conformance

How an implementation is shown to draw what React draws: the scenes, the
addresses, the readings, the tolerances, the expectations and the viewer.

`packages/js/dazzui-react` is the standard. A port is not asked to *resemble*
it; it is asked to produce, for every component instance the React example
draws, the same box, the same decoration, the same type and the same colours,
in every theme — and where it cannot yet, to say so in a file that only
shrinks. Conformance is the name the rest of the industry uses for exactly
this arrangement — one specification, several implementations, one test suite
run against each — and it is the name here.

## The shape

```
tools/conformance/
  scenes.json            the contract: every scene and the addresses in it — written by codegen
  tolerances.json        how close is close enough, per kind of value
  expectations/
    flutter.txt          the checks a platform fails today, one per line — committed, only shrinks
    swiftui.txt
    winui.txt
  data/                  a run — gitignored, regenerated by `pnpm conformance`
    run.json             when, at which commit, which platforms
    react/readings.json  the reference, in the same format as everyone else's
    flutter/readings.json
    flutter/images/…
  fixtures/              a made-up run the viewer is developed against
  src/                   the viewer
```

Three kinds of file, and the distinction is the design:

- **`scenes.json` is a contract.** It says what must be drawn. It is generated
  from the React stories by codegen and committed, like every other file
  codegen owns.
- **`data/` is a measurement.** It says what was drawn, on one machine, at one
  commit. It is never committed and never hand-edited.
- **`expectations/` are a statement of the work left.** They are committed,
  reviewed in the change that touches them, and a line may only be deleted.

## Scenes and addresses

Every example in a React story is already compiled by codegen into every
platform's example, so the same tree of kit components exists everywhere.
Codegen is therefore the one place that knows what a scene holds, and it
writes `scenes.json`: for each story, its `Preview` and each of its examples
as a *scene*, and inside each scene every kit element as a *specimen* with an
**address** — the story id, the scene index and the element's position in a
pre-order walk of the compiled tree:

```
button/2/5   →   the sixth kit element in Button's third example
```

The address is the key on every platform. It needs no class name, no
selector and no guessing at which `dz-button` is which: a platform's example
walks the same compiled scene, and the fifth element it draws is the fifth
element React drew. A specimen also carries its `component`, its `axes` (the
props that pick a recipe — `size`, `variant`, `tint`, `state`) and its text,
so the viewer can name it and a reader can find it.

Elements that hold other kit elements — a `Card` around a heading, a
`Button` with a glyph in it — are addressed too and marked `container`, but
only their box is compared: what is inside them is the story's, and belongs
to the specimens inside. The stage — `Row`, `Col`, `Frame`, `Text` — is
never a specimen.

The walk is fixed, because every collector repeats it
(`tools/codegen/scenes.mjs` is the definition):

- **Pre-order**: an element, then the elements among its props in the order
  the story wrote them — into lists and objects, as deep as they go — then
  its children. `<Button shortcut={<KeyCap>⌘S</KeyCap>}>Save</Button>` is
  the button, then the key cap.
- **As first drawn**: every `useState` at its initial value and every
  conditional taken the way that value takes it. What a popup holds before
  it opens is addressed all the same; a collector that cannot see it writes
  no reading, and it is not compared.
- A helper component the story defines is followed into what it returns,
  as codegen inlines it.

A specimen that draws nothing of its own — a provider, a `Tooltip` lending
its trigger a behaviour — has no reading either: its trigger is a specimen
of its own.

## Readings

Each platform runs its own **collector** over its own example, draws every
scene in every theme it carries at a fixed scale (2x) with motion off, and
writes `readings.json`. A scene is drawn alone, in one frame every platform
repeats: 40rem wide, `spacing-6` of padding on `color-surface`, its content
centred, as the example's document column centres a story.

```jsonc
{
  "platform": "flutter",
  "title": "Flutter",
  "role": "implementation",          // "reference" for react
  "collected": "2026-09-30T10:12:00Z",
  "commit": "3f5f202",
  "scale": 2,
  "font": "Inter",                    // the embedded test face, or null
  "themes": {
    "studio-light": {
      "button/2/5": {
        "box": { "width": 71, "height": 24 },
        "values": {
          "corner": 6, "stroke": 1, "strokeColor": "#d8d8dc",
          "fill": "#2f6df6", "ink": "#ffffff",
          "fontSize": 12, "fontWeight": 500, "lineHeight": 16,
          "paddingX": 10, "paddingY": 4, "shadow": null
        },
        "image": "images/studio-light/button-2-5.png"
      }
    }
  },
  "scenes": { "studio-light": { "button/2": "images/studio-light/button-2.png" } }
}
```

Three rules:

- **One vocabulary.** The property names are the conformance tool's, not
  CSS's and not any platform's. A collector translates `border-radius`,
  `BorderRadius.circular` or `CornerRadius` into `corner` before writing.
- **`null` means "cannot read", not "zero".** A SwiftUI view is a value, not
  a tree; it can draw a specimen but cannot always say what colour it
  painted. A property a platform cannot expose is written `null` and scored
  as *unread* — outside the denominator, never a failure. The picture still
  gets compared.
- **The reference is a reading too.** React's collector
  (`packages/js/dazzui-react/example/scripts/conformance.mjs`) draws the
  example's own story components on a page of their own, `conformance.html`,
  in headless Chromium, finds each specimen by following the elements the
  story wrote into React's tree, and writes the same file. It refuses a scene
  whose specimens do not line up, component for component, with
  `scenes.json`. Nothing about the reference is
  special except its `role`; that is what lets a second standard — a Figma
  export, say — be dropped in later as another `reference`.

Every collector also crops each specimen out of the drawn scene and keeps
the whole scene. Scenes are for eyes, side by side in the viewer. Crops are
compared, perceptually and with a threshold, and only when both sides
embedded the same test face: a picture of text in two fonts differs for a
reason that is not the component's.

## Verdicts and tolerances

A verdict is **derived, never stored**. One module, `src/lib/verdict.ts`,
is shared by the viewer and the command-line check, so the two never
disagree about what passed. For each `(theme, address, property)` the
reference and an implementation are compared and the result is one of:

| Verdict | Meaning |
| --- | --- |
| `match` | equal |
| `within` | differs, inside the tolerance for its kind |
| `off` | differs, outside it |
| `unread` | the implementation wrote `null` |
| `missing` | the implementation drew no specimen at this address |

`tolerances.json` names the kinds and their thresholds, once:

- **length** — `0.5` device-independent pixel. On a 2x display that is one
  device pixel, which is the finest thing two text systems agree on. A
  difference of exactly half a pixel is *off*, because a half step is a
  decision in this system (`spacing.0-5`), not noise.
- **colour** — a distance in OKLab, `0.02`, under which two colours cannot
  be told apart on a calibrated display. A colour that is not opaque is
  written `#rrggbbaa`; its distance is weighted by how much of it shows,
  plus the difference in alpha, so two clear colours are the same colour.
- **discrete** — `fontWeight`, `shadow`: equal or off.
- **image** — a perceptual score over the specimen crop, `0.98`, compared
  only when both readings name the same `font`.

A score rolls up as *matched or within* over *everything but unread*:
per property, specimen, scene, story and platform. A specimen is *missing*
as a whole, and counts against every property it should have had.

## Expectations

`expectations/<platform>.txt` lists the checks a platform fails today, one
per line, `theme address property`, sorted, with a blank line and a `#`
comment allowed:

```
# Segmented control: the raised item's shadow is not yet drawn on Flutter
studio-dark  segmented-control/1/2  shadow
studio-light segmented-control/1/2  shadow
```

`pnpm conformance:check` reads the run and the expectations and fails on two
things: a check that is *off* or *missing* and not listed, and a line that is
listed and now passes. The second is what makes the file a ratchet — a fix
has to delete its lines in the same change, and the file is always an honest
account of what is left. Never add a line to make the check pass; a collector
that reads the wrong thing is fixed in the collector.

The file is committed. It is the one place the state of a port is written
down where a review can see it, and it is what a CI gate has to compare
against.

## The viewer

`pnpm conformance:view` serves `tools/conformance` on :5183. It is the React
example's window, put to a different use: the same three full-height columns,
drawn from the kit alone, so that reading conformance feels like reading the
example.

- **The list**, left: the brand, a search, an *Overview* row, then every
  story by name. A row's badge is the number of checks that are off across
  the shown platforms, or nothing when it is clean.
- **The document**, centre, under a toolbar naming the story and how many
  scenes and specimens it has. The overview is a grid of tiles, one per
  story: the reference's rendering of its preview, and under it a meter per
  platform. A story's page is its scenes in order. Each scene is a section:
  the renderings, one column per shown platform, at one scale, in the chosen
  theme; then the specimens as rows of a table with a column per platform,
  each cell a chip saying *n off*, *unread* or *missing*. Opening a row lays
  every property out, reference beside each implementation, and colours the
  ones that are off.
- **The lens**, right: what the document is looked at through. Which
  implementations are shown, each with its score for the story in view; which
  theme, and which half of it; and whether to show everything, only what
  differs, or only what a platform could not read. The run's date and commit
  sit at the bottom, because a measurement without them is an impression.

The address is the state, as in the example: `?theme=ember-dark`,
`&platforms=flutter,swiftui`, `&show=off`, and `#/button` for the page. A
link is a complete description of what it shows.

## Commands

```bash
pnpm conformance          # collect every platform's readings into tools/conformance/data/
                          #   --themes drawn|all|<id,…>  --scenes <story,…>  --no-images
pnpm conformance:check    # derive verdicts and hold them to expectations/
pnpm conformance:view     # the viewer on :5183 — over data/ when it exists, fixtures/ otherwise
```

A platform's collector is a script beside its example — `flutter test` for
Flutter, an `xcodebuild test` scheme for SwiftUI, the smoke-test switch for
WinUI — that `pnpm conformance` invokes in turn
(`tools/conformance/scripts/collect.mjs` lists them) and whose only contract
is the file it writes, into the `--out` directory it is handed. The run
copies `scenes.json` and `tolerances.json` beside the readings, so `data/` is
a complete measurement on its own. Collectors take the drawn twelve themes
by default; `--themes all` is every theme the example carries. React's is
the only collector written so far. Adding a platform is a collector and an expectations
file; the viewer and the check learn of it from `run.json`.
